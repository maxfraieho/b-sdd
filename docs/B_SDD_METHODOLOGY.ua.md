# B-SDD: Bitemporal Spec-Driven Development
## Архітектурна специфікація, маніфест методології та універсальний інженерний стандарт

---

## Анотація
Сучасна програмна інженерія дедалі більше спирається на роботу автономних та напівавтономних AI-агентів (Claude Code, OpenAI Codex CLI, Google Antigravity CLI, Cursor, Windsurf). Однак під час тривалих робочих сесій агенти неминуче стикаються з проблемою **Архітектурної деградації (Architecture Drift)** — поступовим розмиванням меж компонентів, воскресінням скасованих рішень, роздуванням контексту та прихованими порушеннями системних контрактів.

**B-SDD (Bitemporal Spec-Driven Development)** — це детермінована інженерна методологія, що об'єднує:
1. **Бітемпоральний реєстр рішень (WHAT):** Архітектурні рішення (ADR), керовані двома незалежними вимірами часу (*дійсний час / valid time* та *системний час транзакції / transaction time*) із прямим графом заміщень (DAG).
2. **Топологічний граф коду (WHERE):** Граф властивостей коду на основі AST (GitNexus), який зіставляє змінені файли з архітектурними компонентами та їхніми залежностями.
3. **Процедурні навички агентів (HOW):** Модульні скіли та плейбуки (`SKILL.md`), які динамічно маршрутизуються агентам і самокристалізуються при повторенні дій ($\ge 2$ разів).
4. **Детермінований Pre-Flight компілятор (WHEN):** Надшвидкий (<20 мс), легкий (<500 слів), беззалежний компілятор, який готує робочий контекст правил перед першим кроком агента.
5. **Автоматизовані архітектурні фітнес-тести (VERIFY):** Безперервні тести (`pytest`), які перевіряють затримку, бюджет токенів, чистоту залежностей та цілісність DAG як виконуваний код.

$$\text{B-SDD} = \text{Бітемпоральні інваріанти} + \text{AST-маршрутизація} + \text{Процедурні скіли} + \text{Детермінований компілятор} + \text{Фітнес-шлюзи}$$

## 1. Чому існуючі підходи зазнають невдачі (Криза Architecture Drift)

```
+---------------------------------------------------------------------------------------------+
|                               СПЕКТР АРХІТЕКТУРНОГО ДРЕЙФУ                                  |
|                                                                                             |
|   [ Статичні правила (.cursorrules) ]    [ Наївний векторний RAG ]     [ Звичайні скіли ]   |
|   - Роздування контексту (>2000 слів)    - Ймовірнісний пошук за косинусом - Знають ЯК робити |
|   - Немає механізму заміщення рішень     - Воскрешає застарілий код    - Не знають меж      |
|   - Взаємовиключні інваріанти            - Плутається у схожих словах  - Не знають заборон  |
|                                                                                             |
|                                         V                                                   |
|                         [ Детермінований B-SDD Framework ]                                  |
|                         - Бітемпоральний DAG: valid_to = NOW                                |
|                         - Математичне відсікання старих рішень                              |
|                         - Pre-Flight компіляція < 20 мс, < 500 слів                         |
|                         - Автономні фітнес-тести (pytest 5/5)                               |
+---------------------------------------------------------------------------------------------+
```

### 1.1. Статичні файли правил (`.cursorrules`, `.windsurfrules`, Copilot Instructions)
- **Принцип:** Статичний markdown-файл цілком передається у кожен промпт моделі.
- **Фатальний недолік:** З ростом проекту обсяг правил перевищує 2000–5000 токенів. Коли команда змінює технологію $A$ на технологію $B$, розробники дописують нові правила, не видаляючи старі. Агент отримує взаємовиключні інструкції, втрачає фокус і галюцинує застарілий код.

### 1.2. Наївний векторний RAG (LangChain, LlamaIndex, MemGPT / Letta)
- **Принцип:** Документи архітектури нарізаються на фрагменти, ембеддяться та шукаються за семантичною близькістю вектора запиту.
- **Фатальний недолік (Supersession Failure):** Векторний пошук вимірює *семантичну схожість*, а не *хронологічну істинність*. Якщо `ADR-008` описував *"Пряму інтеграцію Stripe"*, а `ADR-013` постановив *"Stripe заборонено, переходимо на швейцарський QR-bill"*, семантичний пошук на запит *"Як обробляти платежі?"* витягне обидва документи, бо в них однакові ключові слова. Агент відновлює застарілий заборонений патерн.

### 1.3. Ізольовані процедурні скіли (Anthropic MCP, Claude Code Skills)
- **Принцип:** Модульні каталоги з інструкціями (`SKILL.md`) та інструментами.
- **Фатальний недолік:** Навички дають агенту руки (**ЯК**), але нічого не знають про системні обмеження проекту (**ЩО ЗАБОРОНЕНО**). Скіл веб-розробки не знає, що в конкретному банківському додатку заборонено завантажувати сторонні CDN-шрифти або вимагається сувора бітемпоральна ізоляція.

### 1.4. Рішення B-SDD
B-SDD вирішує цю проблему математичним детермінізмом:
- Інваріанти зберігаються у бітемпоральному реєстрі, де у заміщених рішень `valid_to = CURRENT_TIMESTAMP`.
- Pre-flight компілятор виключає будь-яке правило, де `valid_to < NOW`.
- У промпт агента потрапляють виключно активні правила під змінені файли з лімітом до 500 слів.

## 2. П'ять фундаментальних стовпів B-SDD

### Стовп 1: Бітемпоральна істина (Utopia DB)
У класичних базах оновлення перезаписує історію. У B-SDD архітектурні рішення зберігаються за стандартом SQL:2011:
- **Дійсний час (`valid_from`, `valid_to`):** Інтервал, коли правило має юридичну та технічну силу в коді.
- **Час транзакції (`tx_from`, `tx_to`):** Час фізичного запису рішення у незмінний журнал.

```sql
-- Атомарне заміщення рішення в Utopia DB
SELECT intent_store.register_and_supersede_intent(
    p_intent_key      := 'ADR-021',
    p_component       := 'api',
    p_rule_type       := 'invariant',
    p_scope           := 'global',
    p_target_key      := 'WebSocket Notification Protocol',
    p_target_value    := 'Усі сповіщення реального часу передаються виключно через WSS.',
    p_source_file     := 'docs/adr/ADR-021-websocket-notifications.md',
    p_source_hash     := 'e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855',
    p_supersedes_adr  := 'ADR-014',
    p_reason          := 'Висока затримка long-polling на мобільних клієнтах'
);
```

### Стовп 2: Топологічний граф коду (GitNexus)
B-SDD звертається до графа властивостей коду GitNexus (`.gitnexus/index.sqlite`). При модифікації файлу:
1. GitNexus виявляє рекурсивні зв'язки викликів та межі компонентів.
2. Автоматично обчислюються зачеплені архітектурні домени (`core`, `api`, `web`, `database`).
3. Компілятор активує лише ті інваріанти та скіли, які стосуються цих доменів.

### Стовп 3: Життєвий цикл скілів та Правило двох (The Rule of 2)
B-SDD чітко розмежовує *декларативні межі* (ADR) та *процедурне виконання* (Skills):
- **Маршрутизація:** Компілятор генерує блок `RECOMMENDED PROCEDURAL SKILLS` у `.context/active_rules.md`.
- **Вибір:** Агент обирає скіл під завдання (`architecture-designer`, `safe-refactor`, `frontend-design`).
- **Пошук відсутнього:** Якщо скіла немає в наборі, викликається `find-skills`.
- **Правило двох (Самоорганізація):**
  $$\text{Повторюваність процесу} \ge 2 \implies \text{Обов'язкова кристалізація через } \texttt{skill-creator}$$
  Якщо будь-яка інженерна операція чи ланцюжок дій повторюється 2 або більше разів без формалізованого скіла, агент зобов'язаний створити новий перманентний скіл `.agents/skills/<new-skill>/SKILL.md`.

### Стовп 4: Детермінований Pre-Flight компілятор
Компілятор (`src/core/compiler.py`):
- Працює на **100% чистій стандартній бібліотеці Python** (нуль сторонніх пакетів).
- Компілює правила за **<20 мс** завдяки in-memory кешуванню mtime файлів та SQLite.
- Суворо утримує обсяг правил **до 500 слів**, запобігаючи перевантаженню вікна контексту моделі.

### Стовп 5: Автоматизовані архітектурні фітнес-тести
CI/CD та pre-commit перевіряють 5 критеріїв придатності у `tests/test_architecture_fitness.py`:
1. `test_compile_latency_sub_50ms`: Затримка компіляції < 50 мс.
2. `test_context_budget_sub_500_words`: Обсяг промпту <= 500 слів.
3. `test_zero_third_party_dependencies_in_src`: Чистота кодової бази `src/`.
4. `test_supersession_dag_mathematical_pruning`: Повна відсутність заміщених правил у вихідному зрізі.
5. `test_procedural_skill_recommendation_present`: Цілісність маршрутизації скілів.

## 3. 6-фазний життєвий цикл розробки в B-SDD

```
[ Фаза 0: Pre-Flight Hook ]
       │  (run_agy.sh / b-sdd compile)
       ▼
[ Фаза 1: Компіляція правил та скілів ] ───> .context/active_rules.md (<20 мс, <500 слів)
       │                                     - Обов'язкові інваріанти
       │                                     - Рекомендовані процедурні скіли
       ▼
[ Фаза 2: Підбір та пошук скілів ] ────────> Агент обирає скіли (або find-skills)
       │
       ▼
[ Фаза 3: Оформлення специфікації ] ───────> specs/<NNN-feature>/ (spec.md, plan.md, tasks.md)
       │
       ▼
[ Фаза 4: Виконання у коді ] ──────────────> Код пишеться суворо за інваріантами та скілами
       │
       ▼
[ Фаза 5: Фітнес-шлюз (Verification) ] ────> pytest tests/test_architecture_fitness.py (5/5 OK)
       │
       ▼
[ Фаза 6: Кристалізація (Rule of 2) ] ─────> Якщо дія повторилася >=2 разів: skill-creator!
```

## 5. Швидка довідка CLI B-SDD

B-SDD містить консольну утиліту з нулем сторонніх залежностей (`src/cli/main.py`):

```bash
# Компіляція активного зрізу правил для проекту
python3 -m src.cli.main compile

# Компіляція правил під конкретні змінені файли
python3 -m src.cli.main compile --files src/core/compiler.py

# Повна синхронізація намірів та сутностей із базою Utopia DB
python3 -m src.cli.main sync --kb 01a08474-0000-7000-8000-000000000001

# Запуск архітектурних фітнес-тестів
python3 -m src.cli.main fitness

# Ініціалізація структури B-SDD у новому або існуючому проекті
python3 -m src.cli.main init --name "Мій новий проект"

# Створення нового шаблону архітектурного рішення (ADR)
python3 -m src.cli.main adr new "Kafka Event Streaming" --component core --supersedes ADR-002
```

## 6. Висновок
Методологія B-SDD перетворює розробку з AI-агентами із ненадійного підбору промптів на математично сувору інженерну дисципліну. Завдяки бітемпоральному журналу рішень, графу залежностей коду, процедурним навичкам та автоматичним фітнес-шлюзам, команди можуть впевнено створювати масштабні системи без ризику архітектурної деградації.
