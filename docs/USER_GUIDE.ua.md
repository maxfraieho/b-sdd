# Розділ 1. Маніфест, математична модель та фундаментальні принципи B-SDD

## 1.1 Що таке B-SDD (Bitemporal Spec-Driven Development)?

**B-SDD (Bitemporal Spec-Driven Development)** — це передова інженерна методологія для автономних агентів штучного інтелекту та інженерів-архітекторів, яка повністю усуває архітектурну деградацію (*context drift*), втрату вимог та розрив між візуальним моделюванням і реалізацією коду.

Традиційні підходи до розробки з ШІ страждають від трьох хронічних хвороб:
1. **Шум та галюцинації контексту:** Агенти отримують сотні неструктурованих файлів, забувають початкові обмеження й порушують архітектуру вже на 3–5 ітерації.
2. **Неможливість аудиту в часі:** Архітектурні рішення фіксуються розмито в коммітах або чатах, що унеможливлює перевірку «що було істиною на момент транзакції $T$ проти дійсного часу $V$».
3. **Розрив між кодом і моделями:** Схеми у візуальних редакторах існують окремо від робочого коду та тестів, швидко перетворюючись на застарілі малюнки.

B-SDD об'єднує 5 фундаментальних стовпів у математично доведену систему:

$$\text{B-SDD} = \underbrace{\text{Бітемпоральні інваріанти (Utopia DB)}}_{\text{ЩО (Межі та Заборони)}} + \underbrace{\text{AST Граф коду (GitNexus)}}_{\text{ДЕ (Топологія компонентів)}} + \underbrace{\text{Процедурні скіли (MCP)}}_{\text{ЯК (Плейбуки та Інструменти)}} + \underbrace{\text{Детермінований компілятор}}_{\text{КОЛИ (Pre-Flight <20мс)}} + \underbrace{\text{Фітнес-шлюзи}}_{\text{ПЕРЕВІРКА (pytest 100%)}}$$

---

## 1.2 Бітемпоральна шкала: Час дійсності ($T_v$) проти Транзакційного часу ($T_t$)

Будь-яке архітектурне твердження, правило чи рішення (ADR) у системі B-SDD вимірюється у двох незалежних часових вимірах:
1. **Valid Time ($T_v$, Час дійсності):** період у реальному світі, коли архітектурне правило вважається дійсним (наприклад, з моменту затвердження стандарту до моменту його заміни). Позначається інтервалом $[V_{start}, V_{end})$.
2. **Transaction Time ($T_t$, Транзакційний час):** фізичний момент запису рішення в систему (коміт у Git або запис у WORM-леджер). Інтервал $[T_{start}, T_{end})$.

### Математичне правило бітемпорального зрізу:
Для будь-якого запиту стану системи в часовій точці $(v, t)$ агент отримує виключно ті правила $R_i$, для яких:

$$R_i \iff (V_{start} \le v < V_{end}) \land (T_{start} \le t < T_{end})$$

Усі застарілі, скасовані або замінені (superseded) рішення математично відсікаються з контексту ШІ. Це гарантує, що робочий контекст моделі містить **нуль шуму** і **100% актуальних вимог**.

---

## 1.3 П'ять фундаментальних аксіом B-SDD

1. **Специфікація як єдине джерело істини (ADR-001):**
   Жоден рядок коду не пишеться без попередньої формальної специфікації в `specs/`. Будь-які зміни в інтерфейсі чи логіці починаються з оновлення графа специфікації.
2. **Детермінований передпольотний компілятор (ADR-002):**
   Перед початком кожної сесії чи спринту автоматичний компілятор правил (`BSDDCompiler`) аналізує змінені файли та генерує компактний знімок активних інваріантів:
   - **Час компіляції:** строго $< 50$ мс (гарячий кеш $< 5$ мс).
   - **Бюджет слів:** строго $\le 500$ слів.
3. **Чисте стандартне середовище (ADR-002 Pure Runtime):**
   Усе ядро B-SDD (компілятор, парсери, валідатори, адаптери) працює виключно на стандартній бібліотеці Python (`urllib`, `subprocess`, `sqlite3`, `json`). Жодних важких зовнішніх пакетів у runtime.
4. **Правило двох (Rule of 2 / Self-Authoring Skills):**
   Будь-який інженерний або операційний процес, повторений агентом або людиною двічі або більше разів, обов'язково кристалізується в автономну процедурну навичку (`skill`) через майстер `skill-creator`.
5. **Граф статичного інтелекту GitNexus:**
   Зміни у вихідному коді аналізуються на рівні абстрактного синтаксичного дерева (AST). Зв'язки між функціями, модулями, файлами та бітемпоральними доменами прораховуються графовим рушієм GitNexus.

# Розділ 2. Життєвий цикл розробки: Фази Φ1–Φ7 та ланцюжки спринтів

## 2.1 Семифазний життєвий цикл B-SDD ($\Phi 1$ – $\Phi 7$)

Кожна задача, фіча або дефект у системі B-SDD розробляється строго через 7 послідовних фаз. Жоден етап не може бути пропущений або виконаний не за порядком.

```
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │   Фаза Φ1    │ ──► │   Фаза Φ2    │ ──► │   Фаза Φ3    │ ──► │   Фаза Φ4    │
  │ Intent Frame │     │ DRAKON Model │     │ TDD Harness  │     │ Pure Runtime │
  └──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
                                                                        │
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐            │
  │   Фаза Φ7    │ ◄── │   Фаза Φ6    │ ◄── │   Фаза Φ5    │ ◄──────────┘
  │ Distillation │     │ HITL Gate    │     │ Fitness Gate │
  │ & Chaining   │     │ Crypto Sign  │     │ 100% pytest  │
  └──────────────┘     └──────────────┘     └──────────────┘
```

---

### Фаза $\Phi 1$: Intent Framing (Формулювання архітектурного наміру)
- **Артефакт:** `specs/<sprint_id>/spec.md`
- **Вимоги:**
  - Опис проблеми, діючих обмежень та кінцевого стану.
  - Прив'язка до канонічних ADR (наприклад, ADR-001, ADR-008).
  - Жорсткий ліміт розміру: строго $< 500$ слів. Довгі описи відхиляються компілятором як порушення інваріанту лаконічності.

---

### Фаза $\Phi 2$: Visual Flow Modeling (ДРАКОН-моделювання)
- **Артефакт:** `specs/<sprint_id>/logic.drakon.json`
- **Інваріанти ДРАКОН (ADR-008):**
  - **Нуль перетинів ($C = 0$):** Лінії з'єднань між блоками ніколи не перетинаються.
  - **Вертикальний шампур (Happy Path):** Головний успішний сценарій алгоритму завжди прямує строго зверху вниз по вертикалі ($X = 0$).
  - **Правило правого крила:** Будь-які умови, запитання, відхилення або обробка помилок направляються строго праворуч ($X > 0$).
  - **Один вхід — один вихід:** Кожен алгоритм завершується чітко визначеним термінальним вузлом.

---

### Фаза $\Phi 3$: TDD Harness (Тестовий каркас)
- **Артефакт:** `tests/test_<feature>.py`
- **Вимоги:**
  - Тести пишуться **до** реалізації коду.
  - Перевіряється планарна валідність графа ДРАКОН (`DrakonValidator`).
  - Перевіряється бітемпоральна поведінка та відсутність зовнішніх сторонніх залежностей.

---

### Фаза $\Phi 4$: Pure Implementation (Чиста реалізація)
- **Артефакт:** Вихідні модулі в `src/` та компоненти в `b-sdd-ui/src/`
- **Вимоги:**
  - Тільки стандартна бібліотека Python у `src/`.
  - Суворе дотримання типізації TypeScript у `b-sdd-ui/`.
  - Відповідність дизайну швейцарському стандарту Astryx (ніяких довільних hex-кольорів, тільки семантичні токени `var(--astryx-*)`).

---

### Фаза $\Phi 5$: Automated Fitness Gates (Шлюзи фітнес-тестів)
- **Команда:** `pytest -v tests/`
- **Критерій проходження:**
  - 100% тестів успішні (жодного `failed` або `skipped` через баги).
  - Тест швидкодії компілятора: `test_compile_latency_sub_50ms` пройшов.
  - Тест бюджету слів: `test_context_budget_sub_500_words` пройшов.

---

### Фаза $\Phi 6$: Cryptographic HITL Review Gate (Шлюз людини-архітектора)
- **Артефакт:** Незмінний WORM-запис з цифровим підписом.
- **Вимоги (ADR-007, ADR-011):**
  - Оператор у Workbench переглядає зведення спринту.
  - **При Approve (Схвалення):** Браузер генерує WebCrypto підпис (HMAC-SHA256/Ed25519), бекенд верифікує підпис та фіксує перехід до $\Phi 7$.
  - **При Reject & Branch (Відхилення):** Система автоматично створює фізичну Copy-on-Write (COW) гілку в Git (`git branch cow-branch-...`), завершує відхилену лінію ($V_{end} = NOW$) і скидає контекст на $\Phi 1$ з вектором негативних інваріантів $\Delta C$.

---

### Фаза $\Phi 7$: Distillation & Sprint Chaining (Дистиляція та ланцюжок)
- **Принцип ланцюжка (Sprint Chaining):**
  Кожен спринт після завершення $\Phi 6$ генерує не просто звіт, а **готовий до виконання виконуваний `.sh` скрипт для наступного спринту**:
  - `run_sprint_007.sh` виконується $\to$ генерує `run_sprint_008.sh`.
  - `run_sprint_008.sh` виконується $\to$ генерує `run_sprint_009.sh`.
  - `run_sprint_009.sh` виконується $\to$ генерує `run_sprint_010.sh`.
  - `run_sprint_010.sh` фіналізує репозиторій, збирає бандл та оновлює продакшн.


---

# Розділ 3. Пайплайн розробника: CLI, ДРАКОН-моделювання та TDD

## 3.1 Основні команди CLI B-SDD

B-SDD містить уніфікований інтерфейс командного рядка на базі Python standard library (`src/cli/main.py`), а також готові оболонкові скрипти.

### 1. Запуск інтерактивного Workbench
```bash
./run_workbench.sh
```
- Піднімає бекенд на порту `8765` (`src/server/workbench_server.py`).
- Піднімає Vite інтерактивний Workbench на `http://localhost:5173`.
- Автоматично звільняє зайняті порти перед запуском.

### 2. Запуск передпольотного компілятора правил
```bash
python3 -m src.cli.main compile
```
- Сканує репозиторій, виявляє активні ADR та інваріанти.
- Генерує знімок `.context/active_rules.md` із часом $<50$ мс і розміром $\le 500$ слів.
- Якщо передати аргумент `--files file1.py file2.ts`, компілятор сфокусується на відповідних архітектурних доменах.

### 3. Валідація ДРАКОН-алгоритмів
```bash
python3 -m src.cli.main drakon validate specs/008-sovereign-copilot-and-gateway/logic.drakon.json
```
- Перевіряє планарність графа, відсутність перетинів $C=0$, наявність заголовка, коректність переходів.

### 4. Генерація коду за схемою ДРАКОН
```bash
python3 -m src.cli.main drakon parse path/to/scheme.drakon.json
```
- Експортує логіку схеми у структуроване синтаксичне дерево (IR) або скелет функції на Python.

### 5. Синхронізація сесії та генерація Handoff
```bash
# Дистиляція поточної сесії:
python3 -m src.cli.main distill

# Створення контракту передачі наступному агенту:
python3 -m src.cli.main handoff --prompt "Опис задачі наступного спринту"
```

## 3.2 Пайплайн створення нового архітектурного рішення (ADR)

1. **Створення файлу:** Створіть файл у `docs/adr/ADR-XXX-назва.md` за форматом MADR 3.0:
   ```markdown
   # ADR-013: Назва архітектурного рішення

   - **Status:** proposed | accepted | superseded by ADR-YYY
   - **Valid-Time:** [2026-09-17, infinity)
   - **Transaction-Time:** [2026-09-17, infinity)
   - **Component:** core | server | ui | drakon | adapters
   - **Severity:** normal | critical

   ## Context & Problem Statement
   Чіткий опис проблеми, контексту та обмежень.

   ## Invariants
   1. **ADR-013-INV-01:** Формальне твердження обов'язкового правила.

   ## Decision Outcome
   Обране рішення, наслідки та компроміси.
   ```
2. **Верифікація компілятором:** Запустіть `python3 -m src.cli.main compile` — нове рішення автоматично додасться до інваріантів системи.
3. **Супресія (Заміна):** Якщо нове рішення замінює старе (наприклад, ADR-013 замінює ADR-003), у шапці нового вказується `supersedes: [ADR-003]`, а в старому встановлюється `Status: superseded` та $V_{end} = NOW$. Старе рішення більше ніколи не потрапить у контекст агента.

## 3.3 Правило двох (The Rule of 2) для автономних навичок

Коли ви помічаєте, що інженерна послідовність дій (наприклад, деплой на Cloudflare Pages, генерація звіту для Kindle, індексація графа коду) повторюється $\ge 2$ разів:
1. Запустіть створення навички агента:
   ```bash
   python3 -m src.cli.main skill create --name "my-workflow-skill"
   ```
2. Навичка зберігається в `.agents/skills/<name>/SKILL.md` і стає першокласним інструментом, доступним для автономного виконання будь-яким ШІ-агентом.

## 4.2 Граф інтелекту коду GitNexus (ADR-005)

### Навіщо потрібен GitNexus?
У великих мультирепозиторіях звичайний повнотекстовий пошук (grep/ripgrep) є сліпим до семантики мови програмування. Він не розуміє, хто викликає метод, де він визначений, які класи від нього залежать і які побічні ефекти виникнуть при рефакторингу.

**GitNexus** парсить репозиторій за допомогою Abstract Syntax Tree (AST), виділяє символи (функції, класи, змінні, імпорти) і будує орієнтований граф залежностей у графовій базі LadybugDB.

### Робота з GitNexus на хості `192.168.3.184:4747`:
1. **Індексація репозиторію:**
   ```bash
   # Запуск індексації всередині контейнера gitnexus-server:
   docker exec gitnexus-server gitnexus analyze --index-only /projects/b-sdd
   ```
2. **Ігнорування шумних файлів (`.gitnexusignore`):**
   Обов'язково виключайте логи, кеші та збірки, щоб не перевантажувати пам'ять:
   ```
   *.log
   node_modules/
   dist/
   build/
   .pytest_cache/
   ```
3. **Запити до графа знань коду:**
   - **Пошук процесу та символу:**
     ```bash
     docker exec gitnexus-server gitnexus query -r b-sdd 'BSDDCompiler'
     ```
   - **Аналіз контексту методу (хто викликає і кого викликає):**
     ```bash
     docker exec gitnexus-server gitnexus context -r b-sdd 'handle_post_copilot_proxy'
     ```
   - **Аналіз впливу змін (Impact Analysis):**
     ```bash
     docker exec gitnexus-server gitnexus impact -r b-sdd 'src/server/workbench_server.py'
     ```

## 4.3 Робота у мультирепозиторійному середовищі

B-SDD проєктувався для керування одразу багатьма спорідненими проєктами через єдину консоль:
1. **GitHub Live Sync (`src/adapters/github_sync.py`):**
   - Консоль оператора взаємодіє з GitHub API акаунта `maxfraieho`.
   - Завантажує список активних репозиторіїв (`b-sdd`, `utopia-vault`, `drakon.tech`, `ai-drakon-scaffolder`, `send-to-kindle` тощо).
   - Кешує стан репозиторіїв на диск у `.context/github_repos_cache.json` для збереження 100% офлайн-працездатності (ADR-011).
2. **Перемикання контексту через Project Switcher:**
   - У Workbench натискання кнопки `Проєкти та GitHub` (іконка папки з Git) відкриває модальне вікно вибору репозиторію.
   - Вибір проєкту автоматично фокусує граф GitNexus та бітемпоральну шкалу на історії обраного репозиторію.

# Розділ 5: Керівництво користувача B-SDD Developer Workbench UI

B-SDD Developer Workbench (`b-sdd-ui`) — це веб-орієнтоване середовище візуального інженерного контролю, розроблене для моніторингу бітемпорального стану архітектури, верифікації фазових переходів (HITL Gates) та інтерактивного аналізу алгоритмічних дерев ДРАКОН.

Інтерфейс розгорнуто в продуктивному середовищі Cloudflare Pages: [b-sdd-ui.pages.dev](https://b-sdd-ui.pages.dev).

## 1. Топологія та Зонування Інтерфейсу

Інтерфейс побудований на базі дизайн-системи Astryx і складається з чотирьох основних операційних зон:

```
+-----------------------------------------------------------------------------+
|  Зона A: Global Top Header & Telemetry Bar                                  |
|  [Логотип B-SDD] [Селектор Репозиторію] [Фазовий Степпер] [AST Health] [Сесія] |
+----------------------------------------------------+------------------------+
|                                                    |                        |
|  Зона B: Інтерактивний DRAKON Canvas               |  Зона C: Бітемпоральна |
|  - Візуалізація алгоритму без перетинів ліній (C=0)|  Панель Інспекції      |
|  - Планарний шампур (Happy Path)                   |  - Деталі вузла        |
|  - Бітемпоральний міст станів (Active/Bypassed)    |  - Валідність (Tv/Tt)  |
|  - Навігаційне колесо (Zoom / Pan / Fit)           |  - Вплив на AST граф   |
|                                                    |                        |
+----------------------------------------------------+------------------------+
|  Зона D: Bitemporal Timeline & Git Commit Slider                            |
|  [<< Початок] [ < Попередній ] [ Слайдер Історії / Хеш ] [ Наступний > ] [>>] |
+-----------------------------------------------------------------------------+
```

### 1.1. Зона A: Верхня Панель Телеметрії (Global Header)
- **Селектор репозиторію (Multi-Project Hub):** Дозволяє миттєво перемикатися між зареєстрованими репозиторіями (`b-sdd`, `send-to-kindle`, `utopia-db`, `open-notebooklm`).
- **Фазовий степпер (Phase Stepper):** Відображає поточну фазу життєвого циклу (від Φ1 Intent Intake до Φ7 Archive/Handoff) з візуальними маркерами блокування / готовності.
- **Індикатор AST Health:** Показує стан актуальності дерева синтаксичного аналізу (Clean, Stale, Drift Detected).
- **Кнопка сесійного бекапу:** Миттєва фіксація стану в WORM-кеш.

### 1.2. Зона B: Інтерактивний Canvas ДРАКОН (Visual Logic Canvas)
- **Алгоритмічний шампур (Planar Skewer):** Головний успішний сценарій (Happy Path) пролягає строго по вертикальній лінії зліва направо та зверху вниз.
- **Відсутність перетину ліній ($C=0$):** Архітектурний інваріант DRAKON унеможливлює візуальну плутанину.
- **Селектор алгоритмів:** Вибір між канонічними процесами:
  - *Sprint Chaining Algorithm (ADR-007)*
  - *AST Routing Engine (ADR-004)*
  - *Rule of 2 Skill Lifecycle (ADR-003)*
  - *Deterministic Pre-Flight Gate (ADR-002)*
  - *Bitemporal Intent Graph (ADR-001)*

### 1.3. Зона C: Панель Архітектурної Інспекції (Node Details & Bitemporal Inspector)
- При кліку на будь-який блок алгоритму (Дія, Питання, Шампур, Синхронізація) відображаються:
  - Ідентифікатор вузла та канонічний тип.
  - Пов'язані ADR та архітектурні інваріанти.
  - Горизонти валідності: Час валідності $T_v$ (Valid Time) та Час транзакції $T_t$ (Transaction Time).
  - Стан виконання (Unvisited, Executing, Passed, Failed).

### 1.4. Зона D: Бітемпоральний Слайдер (Git Timeline & Scrubber)
- Інтерактивна шкала часу, що дозволяє «перемотувати» стан кодової бази та архітектурного графа назад у часі.
- Синхронізований із реальними комітами Git та транзакціями бітемпоральної бази знань.

## 2. Ключові Операції та Сценарії Роботи

### Сценарій 1: Верифікація та Проходження HITL Gate (Криптографічний підпис)
Фази Φ1, Φ2 та Φ5 захищені криптографічним бар'єром підтвердження людиною (Human-In-The-Loop):
1. Коли пайплайн зупиняється на фазі (наприклад, Φ2 Intent Lock або Φ5 Fit Gate), кнопка **Sign & Approve** стає активною.
2. При натисканні ініціалізується `WebCrypto API` (алгоритм ECDSA / Ed25519).
3. Здійснюється криптографічний підпис гешу наміру (Intent Hash).
4. Підписаний квиток зберігається в ланцюжку доказів, після чого відкривається доступ до автоматичного переходу на наступну фазу.

### Сценарій 2: Візуальна Діагностика Аномалій в Алгоритмах
1. Відкрийте Зону B (DRAKON Canvas).
2. Запустіть покрокову симуляцію або підключіть живий WebSocket/Appwrite стрім.
3. Вузли, на яких виникли помилки попередньої компіляції (Pre-flight assertion failure), підсвічуються червоним кольором (Status: Failed).
4. Натисніть на збійний вузол у Зоні C, щоб переглянути стек трейс, код винятку та інструкції з виправлення за ADR.

### Сценарій 3: Дослідження Історичного Зрізу Кодової Бази
1. Переведіть регулятор у Зоні D на цікавий вам коміт або позначку часу $T_v$.
2. Всі візуальні компоненти (ДРАКОН, список ADR, зв'язки модулів) переходять у режим «ReadOnly Bitemporal Snapshot».
3. Ви бачите систему саме такою, якою вона була в момент виконання транзакції, включно з тодішніми знаннями (Epistemic State).

- Зони A, C та D продовжують повноцінно функціонувати.
- Користувач отримує кнопку **«Відновити зону»** без перезавантаження всієї сторінки.

# Розділ 6: Канонічний Реєстр Архітектурних Рішень (ADR-001 - ADR-012, ADR-FE-001)

Архітектура B-SDD спирається на суворі математичні контракти, зафіксовані у формі Архітектурних Рішень (ADR). Жоден агент або розробник не має права вносити зміни в код всупереч цим інваріантам без явної процедури заміщення (Supersession).

## 2. Короткий Огляд Рішень

### ADR-001: Bitemporal Intent Graph & Transaction Time Horizon
- **Проблема:** Традиційні правила (`.cursorrules`, плоскі файли markdown) або роздувають контекст, або призводять до галюцинацій при зміні вимог. Векторні бази даних (RAG) повертають старі правила разом із новими через однакову семантику.
- **Рішення:** Збереження архітектурних намірів у вигляді орієнтованого ациклічного графа (DAG) у бітемпоральній базі Utopia DB. Кожен запис має дві часові осі: Час валідності ($T_v$) та Час транзакції ($T_t$). Застарілі правила не видаляються, а отримують позначку закінчення дії `valid_to = NOW` та зв'язок `superseded_by`.
- **Інваріант:** Агент отримує лише ті правила, які є валідними на поточний момент ($T_v \le \text{NOW} < T_{v\_end}$).

### ADR-002: Deterministic Pre-Flight Compilation & Sub-500 Word Budget
- **Проблема:** Передача агенту великих обсягів документації деградує увагу моделі (проблема «голки в копиці сіна»).
- **Рішення:** Детермінований компілятор на базі стандартної бібліотеки Python сканує специфікації та ADR, обчислює MD5-хеші та формує ультра-стислий зріз активних інваріантів обсягом строго менше 500 слів за менш ніж 50 мілісекунд.
- **Інваріант:** Жодних сторонніх бібліотек у ядрі `src/core/`.

### ADR-003: Procedural Skill Lifecycle & The Rule of 2 Self-Authoring
- **Проблема:** Інваріанти описують «ЩО заборонено», але не дають алгоритму «ЯК виконувати» складні рутинні операції.
- **Рішення:** Впроваджено життєвий цикл процедурних навичок. Навичка створюється лише тоді, коли аналогічна складна операція була успішно виконана щонайменше 2 рази у різних сесіях (Rule of 2).

### ADR-004: AST Impact Graph Routing
- **Проблема:** Запуск повного набору тестів на кожен дрібний коміт уповільнює розробку, а вибірковий ручний запуск призводить до пропуску регресій.
- **Рішення:** Аналіз синтаксичних дерев (AST) через GitNexus будує граф залежностей та обчислює точний радіус ураження внесених змін, формуючи мінімальний топологічно відсортований набір тестів.

### ADR-005: Automated Architectural Fitness Gates
- **Проблема:** Архітектурна деградація та несанкціоновані імпорти часто виявляються надто пізно.
- **Рішення:** Фаза Φ5 виконує автоматичний аудит: 100% проходження тестів з радіуса ураження, перевірка імпортів через AST-візитор на відповідність шарам архітектури (чиста архітектура).

### ADR-006: Multi-Harness Session Distillation & Context Compaction
- **Проблема:** Довгі сесії накопичують сміття в історії повідомлень, вичерпуючи контекстне вікно та знижуючи точність відповідей моделі.
- **Рішення:** Модуль `SessionDistiller` автоматично дистилює завершену сесію: видаляє проміжні спроби та шуми, виділяє досягнуті результати та залишкові інваріанти у стислий звіт (<4000 токенів), який передається в AI Memory.

### ADR-007: Multi-Session Sprint Chaining & Autonomous Handoff
- **Проблема:** Великі завдання неможливо виконати в межах одного контекстного вікна без ризику втрати контролю.
- **Рішення:** Розподіл завдань на ізольовані автономні спринти. Кожен спринт після завершення формує валідований файл передачі `sprint_handoff.json` та виконуваний скрипт наступного кроку `run_sprint_XXX.sh`.
- **Інваріант:** Кількість порушених інваріантів має строго спадати: $\Delta C = C_{t+1} - C_t \le 0$.

### ADR-008: DRAKON Visual Logic & Developer Workbench
- **Проблема:** Складні алгоритми, описані текстом або заплутаними блок-схемами, важко сприймати людині під час верифікації (HITL).
- **Рішення:** Впровадження ергономічного стандарту ДРАКОН: головний маршрут (Happy Path) завжди йде вертикально по «шампуру», відгалуження помилок — праворуч, лінії ніколи не перетинаються ($C=0$).

### ADR-009: Astryx Design System & Universal Cockpit
- **Проблема:** Візуальний шум та незручне компонування веб-інтерфейсу знижують ефективність інженерного аудиту.
- **Рішення:** Дизайн-система Astryx швейцарської інженерної школи: фіксована висота екрана `100vh` без прокрутки всього вікна, темна палітра Slate, ізольовані робочі зони.

### ADR-010: Universal Multi-Project & Standard Algorithm Catalog
- **Проблема:** Необхідність перемикатися між різними утилітами для моніторингу суміжних сервісів інфраструктури.
- **Рішення:** Інтеграція каталогу репозиторіїв та бібліотеки перевірених часом алгоритмів (каталог шаблонів ДРАКОН для черг, кешування, валідації).

### ADR-011: Live GitHub API Sync & Appwrite Realtime Phase Sync
- **Проблема:** Затримки між локальними змінами агента та їх відображенням на віддалених серверах моніторингу.
- **Рішення:** Двосторонній адаптер синхронізації: локальні фазові переходи транслюються через Server-Sent Events (SSE) у реальному часі, а підписи розробника надсилаються через WebCrypto API.

### ADR-012: Production Deployment & Telemetry Instrumentation
- **Проблема:** Відсутність метрик швидкодії та ризик збоїв при оновленні інтерфейсу в хмарі.
- **Рішення:** CI/CD конвеєр Cloudflare Pages, метрики затримки Pre-Flight компиляції, Prometheus-сумісний експортер стану системи.

### ADR-FE-001: Frontend Cockpit Architecture
- **Проблема:** Аварії в окремих UI-віджетах призводять до падіння всього інженерного кокпіта.
- **Рішення:** Архітектура з нульовим спільним станом збоїв (Zero shared crash state): кожен компонент обгорнутий у `AstryxZoneBoundary`, глобальний стан синхронізується через легковагий Zustand store.


---
