Мета документа: Надати повний, структурований архітектурний контекст та стратегічний зріз системи B-SDD для проведення поглибленого мозкового штурму з моделлю Gemini Pro щодо наступного етапу еволюції інтерфейсу Astryx Cockpit та суверенного бекенду.

--------------------------------------------------------------------------------
1. EXECUTIVE BRIEFING: ПОТОЧНИЙ СТАН СИСТЕМИ (ФІНІШ SPRINT 020)
--------------------------------------------------------------------------------
Методологія B-SDD (Bitemporal Spec-Driven Development) вирішує головну проблему сучасної AI-орієнтованої розробки: «контекстний дрейф» (drift), галюцинації правил та деградацію архітектури в ході тривалих багатосесійних спринтів.

Станом на завершення Sprint 020 у системі реалізовано:
1. Детермінований Pre-Flight Compiler (<50 мс, бюджет <500 слів, 0 сторонніх залежностей у src/core/).
2. Бітемпоральну синхронізацію з Utopia DB на хості 192.168.3.251 (2 часові осі: Valid Time Tv та Transaction Time Tt, WORM-журнал, відсутність деструктивних оновлень).
3. Граф впливу змін (AST Impact Routing) через синтаксичний аналізатор GitNexus.
4. Візуальний ергономічний стандарт ДРАКОН (планарний вертикальний шампур, заборона перетину ліній C=0, вісь X=0).
5. Веб-кокпіт Astryx на React 19 + TypeScript + Vite + Tailwind CSS + Zustand (фіксована висота 100vh no-body-scroll, ізоляція віджетів через AstryxZoneBoundary).
6. Автономну безкоординаторну кластерну мережу (Sovereign Mesh) на хостах .161, .184, .251 з розподіленими лізами на файли (Distributed Leases, TTL).
7. Багатоагентний кворум та арбітраж консенсусу (Autonomous Multi-Agent Consensus, вимога N >= 2/3 схвалення, криптографічні бюлетені голосування Ed25519).
8. Автономний механізм самокорекції та компенсаційного відкату (Self-Correction & Rollback Compensation Engine на базі AST-аналізу помилок).

--------------------------------------------------------------------------------
2. АРХІТЕКТУРНИЙ РОЗРІЗ ФРОНТЕНДУ (ASTRYX COCKPIT): ВИКЛИКИ ТА НАПРЯМКИ ЕВОЛЮЦІЇ
--------------------------------------------------------------------------------
Поточна реалізація b-sdd-ui забезпечує моніторинг інваріантів, відображення графа AST, рендеринг схем ДРАКОН (SVG), інспекцію логів та форму підписання HITL Ed25519.

Критичні завдання для наступних кроків (UX / Frontend Architecture):

2.1. Від пасивного перегляду до Інтерактивного Редактора ДРАКОН (Visual Interactive IDE):
- Проблема: Наразі оператор лише переглядає згенеровані SVG-схеми або завантажує logic.drakon.json. Відсутня можливість інтерактивно коригувати алгоритм мишею/жестами.
- Завдання: Створити повноцінне планарне полотно (Canvas / SVG Engine) з підтримкою Drag-and-Drop блоків ДРАКОН (Заголовок, Дія, Питання, Вибір, Кінець).
- Головний інваріант: Алгоритм автоматичного підтримання планарності C=0 у реальному часі. Під час перетягування вузла інтерфейс повинен математично запобігати перетину ліній та автоматично вирівнювати альтернативні гілки праворуч від основного шампура.

2.2. Візуальний відладчик AST-мутацій (Step-by-Step DRAKON Debugger):
- Проблема: Коли агент виконує рефакторинг або генерацію коду, оператор бачить лише кінцевий diff або консольний вивід.
- Завдання: Покрокове підсвічування вузлів ДРАКОН у реальному часі, коли агент проходить відповідні синтаксичні гілки в AST. Візуалізація змінних та стану тестів прямо на полотні схеми.

2.3. Multi-Agent Quorum Arena & Ballot Streaming:
- Проблема: Процес голосування агентів за схвалення коміту (ADR-019) відбувається у фоні. Оператору складно оцінити аргументи голосуючих сторін у реальному часі.
- Завдання: Спеціалізована панель «Арена Консенсусу»:
  * Жива стрічка криптографічних бюлетенів від агентів кластера (.161, .184, .251).
  * Графічний індикатор досягнення 2/3 кворуму (Progress bar з довірчими інтервалами).
  * Інспектор аргументів вето: якщо агент голосує ПРОТИ, розгортається AST-аналіз порушеного інваріанта.

2.4. Bitemporal Time-Travel Slider (Машина Часу Інваріантів):
- Проблема: Оператор не може наочно побачити, як змінювався граф правил системи у часі.
- Завдання: Подвійний повзунок часу (Valid Time Tv та Transaction Time Tt). Перетягуючи повзунок, оператор бачить топологічний граф правил на будь-яку дату: зелені — щойно прийняті, червоні — заміщені (superseded), напівпрозорі — заплановані майбутні наміри.

2.5. Мапа розподілених лізів (Cluster Lease Visualizer):
- Завдання: Візуальна карта кодової бази (Treemap / Sunburst), на якій підсвічуються файли та модулі, захоплені агентами під лізи: кольорове кодування по агентах, таймери зворотного відліку TTL до вивільнення блокування.

--------------------------------------------------------------------------------
3. АРХІТЕКТУРНИЙ РОЗРІЗ СУВЕРЕННОГО БЕКЕНДУ: ВИКЛИКИ ТА НАПРЯМКИ ЕВОЛЮЦІЇ
--------------------------------------------------------------------------------
Суверенний бекенд B-SDD орієнтований на повну автономність локального кластера, нульову залежність від хмарних RAG-провайдерів та найвищу швидкість реакції.

Критичні завдання для наступних кроків (Backend Architecture):

3.1. Безброкерна шина подій високої пропускної здатності (Sovereign Event Mesh):
- Проблема: Використання важких зовнішніх брокерів повідомлень (Kafka, RabbitMQ) неприпустиме для легковажного суверенного ядра.
- Завдання: Розробка ультра-легковажного механізму трансляції подій між локальними машинами (.161, .184, .251) на базі HTTP/2 Server-Sent Events (SSE), WebSockets або легкої SQLite WORM-черги з нульовою затримкою.

3.2. Механізм формальної верифікації алгоритмів ДРАКОН (Formal Verification Engine):
- Проблема: Валідатор схеми перевіряє структурну планарність (C=0), але не гарантує відсутність нескінченних циклів або недосяжних станів (Unreachable code).
- Завдання: Вбудований двигун формальної верифікації на чистій стандартній бібліотеці Python (або легковажний SMT/SAT солвер), що доводить завершуваність (Termination Proof) та повноту покриття умов гілкування до початку генерації вихідного коду.

3.3. Нативний MCP-сервер B-SDD (Model Context Protocol Gateway):
- Проблема: Зовнішні LLM-агенти (Claude, Gemini Pro, Codex) спілкуються з ядром через CLI або прямі скрипти.
- Завдання: Реалізація єдиного стандартного b-sdd-mcp сервера з інструментами:
  * bitemporal_query_invariants(snapshot_time, component)
  * drakon_validate_and_compile(spec_json)
  * cluster_acquire_lease(file_path, agent_id, ttl)
  * consensus_submit_ballot(proposal_id, vote, signature)
  * ast_impact_radius(diff_patch)

3.4. Ізольовані пісочниці виконання з автоматичним захистом (Sandboxed Pi Workers):
- Проблема: Виконання згенерованого коду може спричинити збої оточення або витік ресурсів.
- Завдання: Жорстка ізоляція термінальних воркерів (cgroups / chroot / micro-sandboxes) з обмеженнями пам'яті/CPU та миттєвим спрацьовуванням компенсаційного відкату при переповненні лімітів.

5. КЛЮЧОВІ ПИТАННЯ ТА ДИЛЕМИ ДЛЯ МОЗКОВОГО ШТУРМУ З GEMINI PRO
--------------------------------------------------------------------------------
1. Алгоритм планарності на клієнті: Який підхід вибрати для підтримки C=0 при ручному перетягуванні вузлів: детермінований покроковий геометричний перерахунок чи комбінацію сіткового прив'язування (grid snapping) з миттєвою девалідацією?
2. Топологія синхронізації кворуму: Як організувати стійкий до розривів мережі консенсус між трьома вузлами кластера без центрального координатора за умови тимчасової ізоляції одного з вузлів?
3. Баланс стиснення контексту: Як зберегти бюджет Pre-Flight компилятора <500 слів при зростанні кількості ADR понад 30–50 штук? Чи потрібна ієрархічна дворівнева схема інваріантів (Core Axioms vs Component Rules)?
4. Інтеграція Astryx UI з MCP: Чи доцільно запускати веб-інтерфейс як MCP App, де клікабельні дії оператора транслюються у виклики інструментів агента?
